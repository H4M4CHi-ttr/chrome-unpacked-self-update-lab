# Chrome 開発者モード向け GitHub Releases 自動更新

[English](README.md) · 日本語

開発者モードで読み込む、パッケージ化されていない Chrome 拡張機能（Manifest V3）を GitHub Releases から自動更新する実装例です。初回に拡張機能のフォルダを選んで読み書きを許可し、自動更新を有効にすると、Chrome の起動中に新しいリリースを確認します。書き込みの許可が有効な間は、ディスク上の JavaScript ファイルを自動で更新できます。Chrome ウェブストア、Native Messaging、実行時の外部プログラムは使いません。

セットアップは「[デモを試す](#デモを試す)」を参照してください。自分の拡張機能に組み込む手順は[移植ガイド](PORTING.md)、AI エージェント向けの案内は [AGENTS.md](AGENTS.md) にあります。

## デモを試す

1. [v1.0.0 の実験用 ZIP](https://github.com/H4M4CHi-ttr/chrome-unpacked-self-update-lab/releases/download/v1.0.0/auto-update-https.zip) をダウンロードして新しいフォルダに展開します。v0.x から試し直す場合も、この ZIP から始めてください。v1.0.0 で配信の署名鍵を切り替えました。
2. Chrome で `chrome://extensions` を開き、開発者モードをオンにします。「パッケージ化されていない拡張機能を読み込む」から、展開した `extension` フォルダを選びます。ツールバーから「GitHub 自己更新実験」を開き、「実行中のコード版」が 1.0.0 であることを確認します。
3. 拡張機能の「HTTPS 更新ページを開く」を押し、表示されたページで「拡張機能フォルダを選ぶ」を押します。手順2で Chrome に読み込んだ **同じ `extension` フォルダ**を選び、読み書きを許可します。Chrome が「サイトアクセス時は常に許可」を表示したら選びます。初回にその選択肢が出ない場合は、更新ページのタブをいったん閉じて開き直し、「保存したフォルダを再許可」を押したときに選べるか確認します。選択肢が出なくても、そのセッションで書き込みの許可が有効な間は自動更新が動作します。
4. 「自動更新を有効にする」を押し、設定ページを閉じます。最初の確認は約30秒後で、その後は5分おきです。すぐに確認するには拡張機能の「今すぐ確認」を押してください。
5. [最新リリース](https://github.com/H4M4CHi-ttr/chrome-unpacked-self-update-lab/releases/latest)に v1.0.0 より新しいバージョンが公開されたら、拡張機能の「実行中のコード版」が更新され、実験ログに `execution-confirmed` が記録されたことを確認します。ディスク上の `active.js` の SHA-256 は適用したリリースの `update.json` にある `file.sha256` と一致します。

拡張機能は OS 上のフォルダを自動で取得できないため、手順3でフォルダを選ぶ必要があります。Chrome が更新ページのサイトに与えるアクセス許可は、選んだフォルダ全体に及びます。この公開デモには実験用のコピーだけを許可してください。別の Chrome プロファイルを使う場合は、拡張機能の読み込みとフォルダへのアクセス許可を同じプロファイルで行います。

## デモの公開スケジュール

GitHub Actions の起動予定は毎時17分・37分・57分です。最新版の公開から60分以上経っていれば、マイナーバージョンを1つ上げて署名付きの更新ファイルと新規インストール用 ZIP を公開します。60分未満の回はビルド前に終了します。

予定した回が見送られたときに備えて、起動時刻を複数設けています。GitHub の混雑時には実行が遅れたり、見送られたりする場合があります。定期公開を止めるには Actions 画面で「Hourly demo release」を無効にします。[ワークフロー](.github/workflows/hourly-demo-release.yml) · [GitHub のスケジュール仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

移植時は毎時の cron をコピーせず、自分のプロジェクトのリリース時に署名付きの配信物を用意してください。拡張機能が5分おきに GitHub Releases を確認する処理は、Chrome 側の設定です。[移植ガイド](PORTING.md)

メンテナーは Actions の「Run workflow」から次のバージョンのビルドと署名を確認できます。「Publish if at least 60 minutes have passed」を選ぶと、定期実行と同じ条件で次のバージョンを公開します。

## 更新の仕組み

1. 拡張機能のサービスワーカーが GitHub Releases の `latest` を確認します。署名を検証し、ZIP から指定の `active.js` だけを取り出します。
2. 検証済みの新しいバージョンがあり、自動更新が有効な場合に限り、サービスワーカーが拡張機能 ID に対応する HTTPS 更新ページをバックグラウンドのタブで開きます。すでに対応するタブがあれば、選択中のタブを切り替えずに再利用します。
3. 更新ページは選択済みのフォルダを開くための情報を IndexedDB から読み出します。書き込みの許可が有効なら、更新前のソースを保存してから `active.js` を置き換えます。Chrome の読み込み元に変更が反映されたことを照合し、対象の拡張機能だけを再読み込みします。
4. 再読み込み後のサービスワーカーは、実行中のバージョンとファイルのハッシュが署名で確認した値と一致することを確かめます。照合の記録を確認した更新ページがバックアップを削除します。

Chrome を閉じている間、拡張機能は動きません。自動更新を有効にしたまま Chrome を再起動すると、アラームがなければ設定し、起動時にもリリースを確認します。アラームはスリープ中の端末を起こしません。毎回正確な時刻に実行されるとも限りません。詳しくは [Chrome のアラーム API](https://developer.chrome.com/docs/extensions/reference/api/alarms) を参照してください。

## 「!」が出たときの対処

拡張機能に「!」が表示されたら、HTTPS 更新ページで理由を確認します。

| 表示 | 操作 |
| --- | --- |
| 許可が必要 | 拡張機能から HTTPS 更新ページを開き、「保存したフォルダを再許可」を押します。前に選んだフォルダへの許可が失われたときだけ、この操作が必要です。 |
| フォルダを選び直す | Chrome に読み込んだときに指定した、同じ `extension` フォルダを選びます。 |
| 中断した更新を確認 | HTTPS 更新ページを開くと、ディスク上のファイルと更新の記録を照合します。「中断した更新を旧版に戻す」を押すと、更新前のソースに戻して監視を止めます。 |
| 自動更新を止める | 拡張機能の「自動更新を停止」を押します。すでに始まった書き込みは完了する場合があります。サイトへの許可も取り消すには、Chrome のアドレスバーのファイルアクセス設定から削除します。 |

再許可が必要だと分かった後は、更新を確認するたびにタブや許可ダイアログを繰り返し開くことはありません。同じ内容の別コピーに一時的に書き込んだ場合は、Chrome の読み込み元との照合で検出し、書き込み前の内容に戻します。外部エディタや同期ソフトが同時に編集したファイルは、自動復元で上書きしません。復旧に必要なブラウザデータが消えた場合に備え、元の配布 ZIP は保管してください。

## 実測結果

実装を読む前に、以下の実測で動作を確認できます。

- アラームによる起動、タブの起動と再利用、実ファイルの書き換えと更新後の動作を確認しました。[HTTPS 更新ページを使った実測](HTTPS-RESULTS.md)
- 拡張機能が直接書き込んだ試験では、リリースの署名検証は通りましたが、拡張機能の再読み込みで許可が `prompt` に戻りました。[拡張機能が直接書き込んだ比較実験](RESULTS.md)
- HTTPS 更新ページにフォルダへのアクセスを許可したうえで、Chrome を完全に終了してから起動したときの動作を記録しました。ホット更新との比較もあります。[許可を持つ処理を分けた比較実験](experiments/permission-isolation/RESULTS.md)

更新するのは既存の `active.js` だけです。`manifest.json` やサービスワーカー内の更新処理は置き換えず、複数ファイルの展開や削除も扱いません。署名付きであっても、Chrome ウェブストア向けの配信にはこの方式を使わないでください。詳しくは [Chrome のリモート配信コードの説明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code) を参照してください。

## テストと更新ページの同期

Node.js 22 以降で、パッケージを追加でインストールせずに実行できます。

~~~powershell
node --test tests/*.test.mjs
node tools/sync-updater.mjs --check
node tools/verify-live-evidence.mjs
node tools/verify-isolation-evidence.mjs
node tools/verify-https-evidence.mjs
~~~

拡張機能と HTTPS ページで共用するファイルを変更したら、`node tools/sync-updater.mjs` を実行します。自分のリポジトリで署名付きの配信を始める場合は、[移植ガイド](PORTING.md)に沿って `create-update.mjs` を使います。`build-fixtures.mjs` は別の鍵でデモを作り直す旧実験用のスクリプトです。実行すると初期コードと公開鍵が置き換わるため、既存のリリースの検証には使えません。

ZIP の処理には fflate 0.8.3 を同梱しています。[MIT ライセンス](extension/vendor/LICENSE.fflate)
