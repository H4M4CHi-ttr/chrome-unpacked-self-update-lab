# Chrome 開発者モード向け GitHub Releases 自動更新

[English](README.md) · 日本語

開発者モードで読み込む、パッケージ化されていない Chrome 拡張機能（Manifest V3）を GitHub Releases から自動更新する実装例です。Chrome の起動中に署名付きのパッケージを適用し、再読み込みによって新しい manifest のバージョンと各ファイルを反映できます。Chrome ウェブストア、Native Messaging、実行時の外部プログラムは使いません。

セットアップは「[デモを試す](#デモを試す)」を参照してください。自分の拡張機能に組み込む手順は[移植ガイド](PORTING.md)、AI エージェント向けの案内は [AGENTS.md](AGENTS.md) にあります。

## デモを試す

1. このソースの `extension` フォルダか、拡張機能内更新に対応したリリースの `auto-update-https.zip` を新規フォルダに展開して使います。対応版の `manifest.json` では `options_ui.page` が `popup.html` です。ZIP 名は旧版と共通です。 [Releases](https://github.com/H4M4CHi-ttr/chrome-unpacked-self-update-lab/releases)
2. `chrome://extensions` で開発者モードをオンにし、「パッケージ化されていない拡張機能を読み込む」で `extension` フォルダを選びます。
3. 初回インストールで拡張機能の「更新設定」が開きます。「拡張機能フォルダを選ぶ」を押し、手順2で読み込んだ同じフォルダへの読み書きを許可します。デモには検証用のコピーを使ってください。タブを閉じた場合はポップアップの「更新設定を開く」から戻れます。
4. フォルダの照合と書き込み許可が済むと、自動更新がオンになります。Chrome の起動中、最初は約30秒後、その後は5分ごとに確認します。「自動更新を停止」でオフにでき、フォルダを再許可した際も停止設定を引き継ぎます。
5. 対応する新版があり、書き込みが許可されていれば、サービスワーカーが更新を適用して拡張機能を再読み込みします。`chrome://extensions` のバージョンと実験ログの `execution-confirmed` で確認できます。許可が `prompt` に戻ったときは候補を保留します。設定タブの「保存したフォルダを再許可」から再開できます。保存済みのフォルダを開き直した際に「サイトアクセス時は常に許可」が表示される場合があります。

拡張機能内で更新する 1 系（`v1.22.0` 以降）は、自動更新がオンで書き込みが許可されていれば、そのまま 2 系に更新できます。

**旧 HTTPS 更新ページ版からの移行**では、旧版で中断中の更新を完了または復元し、監視を停止します。拡張機能内更新に対応した版を一度手動で読み込み、拡張機能の設定タブでフォルダを登録してください。以前の許可は GitHub Pages のオリジンに属します。旧サイトのファイルアクセス許可は Chrome のサイト設定から取り消せます。公開済みの旧版が使うページは互換用に保存しています。

この公開デモに GitHub アクセストークンは不要です。プライベートリポジトリに移植する場合は、ポップアップで対象リポジトリの読み取り専用トークンを登録します。 [プライベートリポジトリの設定手順](PORTING.md#プライベートリポジトリを使う場合)

## デモの公開スケジュール

cron-job.org が毎時0分（日本時間）に `main` の `workflow_dispatch` を `publish=true` で呼び出します。2 系は `v2.0.0` から始まり、以降は `v2.0.1`、`v2.0.2` のようにパッチ番号を1ずつ上げます。署名付きの更新ファイルと新規インストール用 ZIP は、前回の公開から60分以上空けて配布します。公開可能まで残り2分以内なら待機し、それより早い場合はその回を終了します。

定期公開を止めるには cron-job.org で対象のジョブを無効にします。起動用の細粒度トークンはこのリポジトリの `Actions` に読み書き権限を設定します。 [ワークフロー](.github/workflows/hourly-demo-release.yml) · [GitHub の起動 API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)

移植時は毎時の cron をコピーせず、自分のプロジェクトのリリース時に署名付きの配信物を用意してください。拡張機能が5分おきに GitHub Releases を確認する処理は、Chrome 側の設定です。[移植ガイド](PORTING.md)

メンテナーは Actions の「Run workflow」から次のバージョンのビルドと署名を確認できます。「Publish if at least 60 minutes have passed」を選ぶと、定期実行と同じ条件で次のバージョンを公開します。

## 更新の仕組み

1. 拡張機能のサービスワーカーが GitHub Releases を調べ、固定した公開鍵で配信情報の署名を検証します。ZIP と各ファイルのハッシュも署名付きの値と照合します。
2. サービスワーカーは拡張機能の IndexedDB からフォルダのハンドルを取り出し、書き込み許可を確認します。許可があればディスク上のファイルを照合し、バックアップを保存します。インストール記録を使って Chrome が読み込んだフォルダを確認し、管理対象のファイルを更新して、最後に `manifest.json` を書き込みます。
3. 書き込んだファイルを読み返し、`chrome.runtime.reload()` を呼びます。新しいサービスワーカーが実行中のコード、manifest の版、パッケージのハッシュを確認するとバックアップを解放します。書き込み許可が有効なら、設定タブとポップアップを閉じた状態でも適用できます。

Chrome を閉じている間、拡張機能は動きません。自動更新を有効にしたまま Chrome を再起動すると、アラームがなければ設定し、起動時にもリリースを確認します。アラームはスリープ中の端末を起こしません。毎回正確な時刻に実行されるとも限りません。詳しくは [Chrome のアラーム API](https://developer.chrome.com/docs/extensions/reference/api/alarms) を参照してください。

## 「!」が出たときの対処

ポップアップから「更新設定を開く」を押して状態を確認します。

| 状態 | 操作 |
| --- | --- |
| 許可が必要 | 「保存したフォルダを再許可」を押します。署名を確認した候補は保持されます。再許可はユーザーの操作で行います。 |
| フォルダが一致しない | Chrome が読み込んだフォルダを選び直します。別のコピーだった場合はインストール記録を元に戻します。 |
| 更新が中断した | 「中断した更新を旧版に戻す」を押します。復元後は監視も停止します。設定画面自体が壊れて開けない場合は、正常な配布 ZIP から手動で復元してください。ZIP は読み込み先とは別の場所に保管します。 |
| 監視の停止・登録解除 | 「自動更新を停止」は次回以降の監視を停止します。「フォルダ登録を解除」は保存したハンドルと更新候補も破棄します。すでに始まった処理は先に完了する場合があります。 |

## 実測結果

2026年11月20日、Windows 11 の Chrome 157.0.8103.79 で、実際に読み込んだ拡張機能フォルダを更新しました。設定タブを閉じて待つと、アラームで `1.0.0 → 1.1.0 → 1.2.0` と2回続けて更新されました。同じプロファイルで Chrome を起動し直すと、拡張機能の登録は維持され、起動時の確認で `1.3.0` が適用されました。3回とも、Chrome が認識した manifest の版と新しいワーカーで実行したコードの版が一致し、ディスク上の全16ファイルが署名付き ZIP と一致しました。

初回のフォルダ選択後、設定タブを開き直した時点で読み書きの再許可が1回必要でした。その後の3回の更新では追加の許可操作は0回でした。配信にはローカルの GitHub Releases 模擬サーバーと検証用の P-256 署名鍵を使い、アラームは30秒間隔に設定しました。実 GitHub の公開リリース v1.21.0 は別に取得し、署名と全17ファイルを検証しました。この版は旧 HTTPS 方式のホスト権限を含むため、拡張内版は自動適用を拒否しました。 [拡張機能内更新の実機記録](evidence/internal-update.json)

現行版の回帰テストでは、署名付きの更新を取得し、書き込み許可が必要な場合は保留することを確認します。同じ内容の別フォルダは元に戻し、正しいフォルダに適用した場合は新しいワーカーが版とハッシュを確認してからバックアップを解放します。このテストでは Chrome API とファイルハンドルを模擬しています。 [ワーカーのテスト](tests/package.test.mjs)

Windows の Chrome 157 では、ツールバーから同梱の設定タブが開くこと、署名付きの更新候補を保存できることを確認しました。検証用の同一内容のコピーをブラウザのオリジン専用ファイルシステムに用意すると、ワーカーは読み込み元の不一致を検出してコピーを元に戻し、インストール済みのファイルを保持しました。配信にはローカルの模擬サーバーとダミートークンを使っています。 [Chrome でのコピー判定の記録](evidence/internal-copy-check.json)

以下は過去の方式の実機記録です。

- アラームによる起動、タブの起動と再利用、実ファイルの書き換えと更新後の動作を確認しました。[HTTPS 更新ページを使った実測](HTTPS-RESULTS.md)
- 拡張機能が直接書き込んだ試験では、リリースの署名検証は通りましたが、拡張機能の再読み込みで許可が `prompt` に戻りました。[拡張機能が直接書き込んだ比較実験](RESULTS.md)
- HTTPS 更新ページにフォルダへのアクセスを許可したうえで、Chrome を完全に終了してから起動したときの動作を記録しました。ホット更新との比較もあります。[許可を持つ処理を分けた比較実験](experiments/permission-isolation/RESULTS.md)

更新する対象は署名付きの一覧にある配信ファイルです。manifest のバージョン、名前、説明、アイコンなどは自動で更新できます。権限、拡張機能の識別子、署名鍵、設定画面のエントリーポイントを変える場合は、新しい ZIP から手動で読み込み直します。旧版の `active.js` 更新用に `update.zip` も配信します。署名付きであっても、Chrome ウェブストア向けの配信にはこの方式を使わないでください。[Chrome のリモート配信コードの説明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)

## テストとインストール記録

Node.js 22 以降で、パッケージを追加でインストールせずに実行できます。

~~~powershell
node --test tests/*.test.mjs
node tools/build-release.mjs --check-index
node tools/verify-live-evidence.mjs
node tools/verify-isolation-evidence.mjs
node tools/verify-https-evidence.mjs
~~~

ソースを直接 Chrome に読み込む前に `node tools/build-release.mjs --refresh-index` で現在のファイルのハッシュを記録し、検証用のコピーを使ってください。自分のリポジトリで配信するときは、[移植ガイド](PORTING.md)に沿って `build-release.mjs` で署名します。`build-fixtures.mjs` は初期コードと公開鍵を置き換える旧実験用のスクリプトです。

ZIP の処理には fflate 0.8.3 を同梱しています。[MIT ライセンス](extension/vendor/LICENSE.fflate)
