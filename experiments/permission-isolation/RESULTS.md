# 更新処理を分離した場合の権限保持

2方式とも、追加の再許可なしで実際の JavaScript を2回連続で更新できました。対象拡張機能を全体再読み込みする HTTPS 方式でも、更新ページを開いたままなら書き込み許可が維持されました。さらに、HTTPSページで「サイトアクセス時は常に許可」を選んだ後は、Chrome完全終了・再起動後も再許可せず更新できました。

## 検証環境と範囲

2026 年 10 月 26 日、日本時間。Windows 11 Pro、Chrome Stable 155.0.8059.85、開発者モード ON の一時プロファイル「AI Agent」で実施しました。初回のフォルダ選択・許可はユーザーが手動で行い、その後は6秒間隔のタイマーで2回更新しました。ログの時刻は UTC です。

この試験は権限と実行コンテキストの寿命を切り分けるものです。固定のA/Bソースを同梱し、`active.js` のみを置換しています。GitHub Releases の監視、署名確認、ZIP 展開との統合は、この追加プローブには含めていません。

## ホットモジュール方式

| 項目 | 結果 |
| --- | --- |
| 実ファイルの更新 | 0.2.0 → 0.2.1 → 0.2.2 に成功 |
| 新しい JS の実行 | B 専用関数、A 専用関数の順で実行・描画 |
| 各更新前後の許可 | どちらも `granted` |
| 追加の `requestPermission()` | 0 回 |
| 更新時のユーザー操作有効状態 | どちらも `false` |
| 固定画面の実行ID | 維持 |
| 固定サービスワーカーの起動ID | 維持 |

書き換え後、`active.js?hot=<ランダム値>` という自分自身の URL からモジュールをインポートしました。全体の `chrome.runtime.reload()` は呼んでいません。新しいコードの関数を実際に実行しています。

固定サービスワーカーが最初に読み込んだモジュールの版は0.2.0のままです。したがって、この方式は UI などのモジュールを更新する方法であり、サービスワーカー本体や manifest を更新できたという結果ではありません。

証跡: [hot-module.json](evidence/hot-module.json)

## 別 HTTPS ページ方式

HTTPSページ側に、同じ対象フォルダを別途登録しました。拡張機能内の画面は閉じ、HTTPSページだけを開いた状態で2回更新しました。

| 項目 | 結果 |
| --- | --- |
| 実ファイルの更新 | 0.2.2 → 0.2.3 → 0.2.4 に成功 |
| 対象拡張機能の全体再読み込み | 各更新後に成功 |
| 新しいサービスワーカー | 0.2.3、0.2.4 の順で起動 |
| 対象の起動ID | 各更新で変化 |
| HTTPSページの実行ID | 維持 |
| 各更新前後の許可 | どちらも `granted` |
| 追加の `requestPermission()` | 0 回 |
| 更新時のユーザー操作有効状態 | どちらも `false` |

HTTPSページは終了せず、対象の拡張機能だけが再読み込みされました。この構成では、対象拡張機能の更新によって更新ページの許可が失われる問題を回避できています。

証跡: [external-https.json](evidence/external-https.json)、[ディスク上の更新後ハッシュ](evidence/disk-after-external.json)

## Chrome 完全終了後

一時プロファイルの全 Chrome プロセスがなくなったことを確認してから、同じプロファイルを再起動しました。HTTPSページでフォルダハンドルは復元できましたが、最初の `queryPermission()` は `prompt` でした。

続いて、復元したハンドルから `requestPermission()` を呼び、ユーザーが Chrome の「サイトアクセス時は常に許可」を選択しました。この後、再び一時プロファイルの全 Chrome プロセスが終了したことを確認し、同じプロファイルを起動しました。

| 項目 | 結果 |
| --- | --- |
| 保存したハンドルの復元 | 成功 |
| 起動直後の権限 | `granted` |
| 起動後の `requestPermission()` | 呼び出しなし |
| 実ファイルの再更新 | 0.2.4 → 0.2.3 → 0.2.4 の2回に成功 |
| 対象拡張機能の再起動 | 各回で新しい版と起動IDを確認 |
| 各更新前後のHTTPSページの権限 | `granted` を維持 |

再起動後の試験は、新リリース配信の試験ではなく、同梱ソースを往復して保存済みの許可を実際に使えることを確認したものです。検証用プローブの拡張機能は、同じパスから DevTools で再読み込みしています。Chrome起動時に拡張機能や更新ページが自動起動したという結果ではありません。

この環境では、「別HTTPS更新ページがアクセス権を持ち、対象拡張機能だけを再読み込みする」方式で、対象更新ごとの再許可を回避できました。「サイトアクセス時は常に許可」の設定後は、Chrome再起動をまたぐアクセスも確認できました。

## 検査と残る範囲

`node tools/verify-isolation-evidence.mjs` は、両方式とChrome再起動後の各2回の更新、実行、権限、画面・対象の起動ID、ハッシュを確認して成功しました。送信元とメッセージの制限を含むローカルの24件のテストも成功しています。

外部ネイティブプログラム、権限の強制付与、オフスクリーン画面、Chrome の安全機能を無効にする設定は使っていません。観測には Chrome DevTools MCP を接続しています。

PWA のインストール、OS 起動時の実行、バックグラウンドタブの凍結・破棄、スリープ、長期運用は未検証です。HTTPS方式を常用向けにするには、既存の署名付き配信との統合、継続運用向けの鍵管理、更新ページ自身の配信と安全性も検討する必要があります。

実験後は自動実行中の処理を残さず、一時Chromeを終了しました。プローブの作業コピーは配布用の初期版0.2.0へ戻しています。この開発用の復元操作は、上記の更新成功には含めません。
